# 후기 블로그 파이프라인

사진과 대충 한 설명만 주면 네이버 블로그에 후기가 발행된다.
게임 스튜디오 템플릿에서 온 `/blog`·`/shorts`와는 별개이며, 이쪽이 실제로 쓰는 것이다.

## 쓰는 법

```
/review ~/Desktop/성수동파스타 어제 다녀온 곳, 트러플 파스타 맛있었음
```

사진은 **파일 경로**로 줘야 한다. 채팅에 이미지를 붙여넣으면 내용을 읽을 수는
있지만, 그 사진을 네이버에 업로드할 수가 없어서 사진 없는 글이 된다.

## 흐름

```
사진 + 대충 설명
  1. 사진 판독   — 간판→상호, 메뉴판→가격, 영수증→날짜·총액
  2. 스카우트    — 이 집이 뭐로 유명한지 먼저 찾는다  ← 묻기 전에
  3. 인터뷰      — 시그니처부터 묻고, 나머지 빈칸을 채운다
  4. 검색 보강   — 영업시간·주소 등 사실 확인
  5. 작성        — brand-voice 톤으로 (review-writer)
  6. 미리보기    — preview.html 로 발행될 모습 확인
  7. 발행        — 네이버에 자동 업로드 + 장소 카드
```

### 스카우트가 인터뷰보다 먼저인 이유

**이 순서가 이 파이프라인의 핵심이다.** 그 집이 뭐로 유명한지 모르는 채로 질문을
짜면, 어느 블로그에나 있는 네 가지를 묻고 끝난다 — 맛이 어땠어요, 얼마였어요,
아쉬운 점은요, 누구랑 갔어요.

규카츠 이치니산은 **소스를 안 주고 와사비·간장·암염으로 먹는 집이고, 레어로 튀겨
나온 고기를 손님이 돌판 화로에 직접 구워 먹는다.** 독자가 궁금한 건 그게 실제로
어땠느냐이고, 그건 다녀온 사람만 답할 수 있다.

실제로 이 순서가 없을 때 실패했다. 인터뷰에서 소스를 안 물었고, 글이 그대로
완성됐고, 사용자가 뒤늦게 잡아냈다. 검증에서도 재현됐다 — 스카우트 없이 돌린 3번의
인터뷰 중 **시그니처를 제대로 물은 건 0번**이었다. 순서를 바꾸자 3번 다 물었다.

### 1. 사진이 곧 사실

사진을 먼저 다 읽는다. 메뉴판에 가격이 찍혀 있으면 가격을 묻지 않는다. 영수증이
있으면 날짜·총액·주문 내역을 거기서 읽는다. 실제로 사용자가 "와인 한 잔"이라고
했는데 영수증에 `x2`로 찍혀 있던 적이 있다 — 이런 어긋남은 지어내서 메우지 않고
물어본다.

### 2. 되묻기

후기 종류(맛집·여행·제품·장소)를 사진과 설명에서 판단하고,
`content/config/review-types/<종류>.md`의 질문 세트에서 **아직 모르는 것만** 묻는다.
새 종류를 추가하려면 파일 하나 추가하면 된다.

**그 가게 고유의 먹는 방식·이용 방식에 대한 감상은 반드시 인터뷰에서 묻는다.**
나중에 `todo.md`로 미루면 글의 핵심이 빠진 채로 완성돼버린다.

### 3. 지어내지 않는다

사진에도 없고 사용자도 모르고 검색으로도 확인이 안 되면, **그 문장을 본문에서
빼고** `todo.md`에 남긴다. `[확인 필요]`를 본문에 남기면 그대로 발행돼서 독자가
미완성 메모를 읽게 된다. `publish.py`가 본문에 `[확인 필요]`가 있으면 발행을
거부한다 — 코드 레벨 안전장치다.

### 4. 사진은 전부 넣지 않는다

독자에게 도움이 되는 사진만 본문에 배치한다. 영수증·가격표 같은 **증거 사진은
사실을 읽어내는 데 이미 제 역할을 다했으므로** 본문에서 빼도 된다. 사진에 자리를
만들어주려고 "영수증" 같은 소제목을 만들고 있다면 글을 망치고 있는 것이다.

### 5. 미리보기

```bash
.venv/bin/python scripts/naver/publish.py <폴더> --blog-id <아이디> --preview
```

계정도 브라우저 자동화도 없이 `preview.html`이 나온다. **발행에 쓰는 변환기를 그대로
쓰므로** 미리보기가 곧 발행 결과다.

## 톤

`content/config/brand-voice.md`에 있다. 요약하면 **일기형 + 쓸 건 다 쓴다.**

리뷰어가 아니라 "같이 다녀온 친구" 목소리다. 구어체 존댓말, 말줄임표, 이모지를
쓰고 평론가 어투("재료 본연의 맛")는 금지다. 구조는 주제별로 묶지 않고 그날 겪은
순서대로 간다.

단점은 근거와 함께 그대로 쓴다. "별로였어요"가 아니라 "불이 약해서 안 익었어요"로.

**이 톤은 사진이 많아야 성립한다.** 사진 → 짧은 글 → 사진의 리듬이라, 사진이 서너
장뿐이면 글이 짧게 끝난다. 없는 사진을 글로 늘려 때우지 않는다.

## 준비 (최초 1회)

```bash
python3 -m venv .venv
.venv/bin/pip install playwright
.venv/bin/python -m playwright install chromium
.venv/bin/python scripts/naver/login.py --blog-id <네이버아이디>
```

브라우저가 뜨면 직접 로그인한다. 세션이 `secrets/naver-session.json`에 저장되고,
그다음부터는 headless로 발행된다. 이 파일은 **로그인된 계정 그 자체**이므로
공유하면 안 된다 (`.gitignore`에 있다).

## 폴더

```
content/reviews/YYYY-MM-DD-<가게이름>/
├── photos/            # 원본 사진
├── interview.md       # 사진에서 읽은 것 + 사용자 답변
├── research.md        # 검색 보강분 (출처 URL 포함)
├── naver.md           # 발행 본문 (frontmatter: title/tags/place/place_region)
├── todo.md            # 확인 못 한 것 — 본문에 안 들어간다
└── preview.html       # 발행될 모습
```

한 편 = 한 폴더라 중간에 끊겨도 다음 단계부터 이어진다.
`content/reviews/`는 `.gitignore` 처리되어 있다.
